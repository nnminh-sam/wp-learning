### Expectations by Experience Level

In this chapter, we'll look at how system design interview expectations change with your experience level.

# 1. Same Question, Different Expectations

Many companies ask similar system design questions across different experience levels. For example, both a mid-level engineer and a staff engineer might be asked to design a chat application.

The difference lies in what interviewers expect from their answers. They evaluate not just whether your design works, but also how you approach the problem, make technical decisions, and reason through trade-offs.

A design that's considered strong for a mid-level engineer might not be enough for a senior engineer.

That's why, when preparing for system design interviews, it's important to understand not only how to design systems, but also the level of depth, independence, and technical judgment expected for the role you're applying for.

# 2. What the Levels Mean

Before we get into the expectations, let's clarify what these levels mean, since companies use different titles and leveling systems.

However, these levels don't map perfectly across companies. For example, Amazon's Principal Engineer isn't necessarily equivalent to a Staff Engineer elsewhere.

The responsibilities and scope of each role can vary quite a bit:

- A mid-level engineer typically works independently on well-defined features.
- A senior engineer takes ownership of larger projects and helps guide technical decisions within a team.
- A staff engineer often works on problems that span multiple teams.

In a system design interview, interviewers look for evidence that you can operate at the expected level.

Throughout this chapter, we'll use one question, "Design a chat application", to show how a strong answer changes from one level to the next.

# 3. Entry-Level

For entry-level roles, you may not even have a separate system design round. Many companies focus more on coding and computer science fundamentals when interviewing new graduates.

Even when system design comes up, the questions are usually simpler and more focused. For example, you might be asked to:

- Design a basic service
- Extend a coding solution to handle datasets too large to fit in memory
- Explain how a request travels from a browser through the server to the database

At this level, interviewers mainly want to see whether you understand the fundamental components of a system and how they work together. You should be able to explain when to use a relational database, how caching improves performance, and why load balancers are useful.

You're generally not expected to have deep knowledge of topics like consensus algorithms or multi-region failover. What's more important is your ability to explain the fundamentals clearly and reason through unfamiliar problems.

Even if your next interview doesn't include system design, learning these concepts early will give you a strong foundation to build on as you progress in your career.

# 4. Mid-Level

For mid-level engineers, the main expectation is that you can design a complete system that meets the core requirements. You should be able to clarify the requirements, choose appropriate components, and explain how they work together.

You should also understand the components you introduce and be able to explain why they're needed:

- If you add a cache, explain what it stores, how data gets into it, and when cached entries expire.
- If you choose a database, explain why it's suitable for your data model and query patterns.

At this level, it's perfectly normal to receive some guidance from the interviewer. For example, they might ask how your system would handle a sudden increase in traffic. You should be able to think through the problem and suggest reasonable improvements, even if you didn't identify the issue on your own.

So, for mid-level roles, focus on getting the basic design right and covering all the core requirements before moving on to more advanced optimizations.

## 4.1 Example: The Chat Application

At the mid-level, you might start by identifying three core requirements:

- One-to-one messaging
- Real-time message delivery
- Access to conversation history

To support these requirements, we need a few components:

- WebSocket connections: Clients maintain WebSocket connections with chat servers, allowing the servers to push new messages in real time.
- Message database: We store messages durably before acknowledging them to the sender.
- Connection registry: Since users might be connected to different chat servers, we need a way to find which server a recipient is connected to. For this, we can use Redis to maintain a mapping between connected users and their chat servers.

You should then be able to explain the complete message flow. For example, when Alice sends a message to Bob:

- Alice's chat server stores the message in the database and sends an acknowledgment.
- It looks up Bob's chat server in Redis.
- It forwards the message to Bob's chat server for delivery.
- If Bob is offline, the message remains stored, and his client can retrieve it when he reconnects.

This gives us a working design that covers the core requirements. There are still failure scenarios and edge cases to consider, but at this level, the priority is to demonstrate that you understand how the main components work together.

# 5. Senior

For senior-level roles, the expectations go beyond designing a system that works. You also need to identify and address the more challenging parts of the design.

#### Leading the discussion

One major difference is how independently you lead the discussion. As a senior candidate, you should be able to clarify requirements, develop a high-level design efficiently, identify potential challenges, and suggest which areas deserve a deeper discussion.

#### Technical depth

You're also expected to demonstrate stronger technical depth. For example:

- Why did you choose a particular database?
- How would you partition the data as the system grows?
- What happens if a server fails?

You should be able to explain these decisions and how your system would behave under different conditions.

#### Reasoning through trade-offs

Another important expectation is your ability to reason through trade-offs. If you propose adding a cache, don't just say it improves performance. Explain what you're gaining, how stale the cached data might become, and whether that's acceptable for the application.

The interviewer may still ask questions and guide parts of the discussion. But at the senior level, you should be able to recognize important design challenges and address them proactively, rather than waiting for the interviewer to point them out.

Tip

Once you have a working design, a useful habit is to ask yourself: "What breaks first as this grows?" Then bring that up before the interviewer does.

## 5.1 Example: The Chat Application

A senior candidate would start with a basic working design, then explore more challenging problems like message ordering and storage.

#### Message ordering

Messages might arrive out of order when they pass through different servers.

One way to handle this is to route messages for each conversation through a designated server that assigns sequence numbers. Clients can then use these numbers to display messages in the correct order.

You should also explain what happens if that server fails and how another server takes over without assigning conflicting sequence numbers.

#### Storage

Another challenge is handling a large number of conversations and growing message history.

You could partition the message database by conversation ID, making it easier to retrieve messages from the same conversation. However, you'd also need to consider how to distribute conversations across partitions and handle unusually active conversations that generate much more traffic than others.

# 6. Staff

At the staff level, interviewers expect strong technical depth, along with broader judgment about what to build and how to operate the system.

#### Prioritization

You should be able to identify which problems matter most for the product, which ones can wait, and where the team should focus its engineering effort. More importantly, you should be able to explain why those priorities make sense.

#### Operational concerns

While senior engineers are expected to understand reliability, staff-level candidates should be able to explain how deployment strategies, monitoring, and failure recovery affect the system as a whole.

#### How the architecture evolves

Another key expectation is thinking about how the architecture evolves over time:

- What should you build in the first version?
- When would a more complex design become necessary?
- How would you migrate to that design without disrupting existing users?

#### Handling ambiguity

Staff-level interviews can also be less structured. The interviewer might introduce unusual constraints, leave important requirements open-ended, or let you decide which areas to explore in depth.

In these situations, they're evaluating not just your technical decisions, but also how you handle ambiguity, set priorities, and make sound engineering judgments.

## 6.1 Example: The Chat Application

At the staff level, you should be able to connect technical decisions to the product's needs and priorities. For example, an internal company chat tool and a consumer messaging app serving hundreds of millions of users will have very different requirements for scalability, cost, and reliability.

#### Behavior in production

Chat servers maintain long-lived WebSocket connections, so deploying a new version can force clients to reconnect. If too many clients reconnect at once, they could overwhelm the servers.

To avoid this, you might gradually drain connections from servers being replaced and introduce randomized delays before clients reconnect.

#### Monitoring and reliability

You could track message delivery latency for online users and configure alerts when it exceeds acceptable limits. This helps the team detect problems before they affect too many users.

#### Future requirements

You should also consider how future requirements might affect the architecture. Features like group messaging, multi-region support, and end-to-end encryption can introduce significant complexity. For example, end-to-end encryption prevents servers from reading message content, making server-side search more challenging.

At the staff level, the goal is to show that you can make these decisions thoughtfully, balancing current requirements with future needs without introducing unnecessary complexity.

# 7. How to Prepare

You can use these expectations to make your interview preparation more focused.

#### Mid-level

Focus on building strong fundamentals and designing complete systems. Practice developing a clear high-level design in about 20 minutes, leaving enough time to explore the details. Make sure you understand every component you introduce and can explain how the main requests flow through the system.

#### Senior

Practice taking more ownership of the discussion. Once you have a working design, identify potential bottlenecks, failure scenarios, and important trade-offs without waiting for the interviewer to bring them up. You should also develop a deeper understanding of common technologies, including how they work internally and what happens when they fail.

#### Staff

Focus more on real-world engineering decisions. Think about deployments, monitoring, migrations, and operational costs. Practice explaining which problems you'd prioritize, which ones you'd defer, and what might cause you to reconsider those decisions.

The same system design question can be used to evaluate candidates at different experience levels, but the expectations are different.
